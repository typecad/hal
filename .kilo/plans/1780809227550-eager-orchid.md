# Plan: Pre-Scan Unsupported TypeScript Feature Detection

## Goal

Create a pre-scan AST analysis pass that runs **before** IR building to detect TypeScript features that have no C++ equivalent, and report them to the user as clear, actionable warnings with a centralized feature compatibility registry.

## Architecture

### 1. Feature Compatibility Registry

**New file:** `packages/cuttlefish/src/ir/feature-registry.ts`

A machine-readable map of TS syntax kinds to their C++ support status. Each entry contains:
- `kind`: The `ts.SyntaxKind` to match
- `status`: `"unsupported"` | `"approximation"` | `"unsupported-context"`
- `message`: Human-readable explanation of why it's unsupported
- `hint`: Actionable suggestion for what to do instead
- `code`: Diagnostic code (e.g., `"TS2CPP_NO_EQUIVALENT"`)

The registry covers known-unsupported features:

| TS Feature | Status | Reason |
|---|---|---|
| `TaggedTemplateExpression` | unsupported | No C++ equivalent |
| `MetaProperty` (`import.meta`, `new.target`) | unsupported | No C++ equivalent |
| `Object.keys/values/entries` on non-map | unsupported | No reflection in C++ |
| `delete` on non-map | unsupported | No dynamic property deletion |
| `super` outside class method | unsupported | No valid C++ translation |
| Optional chaining (`?.`) | approximation | Lowered with null guard; semantics differ |
| Nullish coalescing (`??`) | approximation | Lowered with polyfill helper |
| `typeof` on non-primitive | approximation | Returns approximate type name |
| `in` operator on non-map | approximation | Lowered to `count()` check |
| `void` expression | approximation | Lowered to `(void)(...)` |
| `RegularExpressionLiteral` | approximation | Lowered to `std::regex` |
| Destructuring without initializer | unsupported-context | No C++ equivalent for uninitialized destructuring |
| Non-identifier declaration names | unsupported-context | Complex patterns unsupported |

### 2. Pre-Scan AST Visitor

**New file:** `packages/cuttlefish/src/ir/feature-prescan.ts`

A standalone function that walks the entire AST before IR building and checks each node against the feature registry. It produces `Diagnostic[]` entries for every match.

```
export function prescanUnsupportedFeatures(
  source: ts.SourceFile,
  sourceText: string,
  boardPackage?: string,
): Diagnostic[]
```

The visitor:
1. Uses `ts.forEachChild` recursively to walk all nodes
2. For each node, checks `node.kind` against the registry
3. For expression nodes, also checks context (e.g., is `delete` applied to a map or a plain object?)
4. Returns an array of `Diagnostic` objects with `code: "TS2CPP_NO_EQUIVALENT"` or `code: "TS2CPP_APPROXIMATE"`

Context-sensitive checks (cannot be done by kind alone):
- `Object.keys/values/entries` — check if receiver is a `Map` type; if not, emit warning
- `delete expr` — check if target is a `Map`/`Set` method call; if not, emit warning
- `PropertyAccessExpression` with `?.` — detect optional chaining
- `BinaryExpression` with `??` — detect nullish coalescing
- `BinaryExpression` with `in` keyword — detect `in` operator on non-map

### 3. Integration into the Transpile Pipeline

**Modified file:** `packages/cuttlefish/src/ir/build-ir.ts`

In `buildProgramIR()`, after parsing the source but before the main `forEachChild` loop (after line ~27), call the pre-scan:

```typescript
const source = parseSource(fileName, normalizedSourceText);
const diagnostics: Diagnostic[] = [];

// Pre-scan for unsupported features
const prescanDiagnostics = prescanUnsupportedFeatures(source, normalizedSourceText, boardPackage);
diagnostics.push(...prescanDiagnostics);
```

This gives the user a **complete list** of unsupported features upfront, rather than discovering them one-by-one during IR building. The existing inline `emitUnsupportedExpression` / unsupported statement handling remains as a safety net for cases the registry doesn't cover.

### 4. Enhanced Diagnostic Messages

The registry provides structured data for each unsupported feature. Example diagnostics:

```
warning [TS2CPP_NO_EQUIVALENT] (12,8): Tagged template expressions have no C++ equivalent.
  ↳  Use a regular template literal (backtick string) or string concatenation instead.

warning [TS2CPP_APPROXIMATE] (24,5): Optional chaining (?.) is approximated with a null guard in C++.
  ↳  The C++ output may behave differently from TypeScript. Use an explicit null check for clarity:
      if (obj !== null && obj !== undefined) { obj.method(); }
```

### 5. Dedicated Diagnostic Codes

| Code | Severity | Meaning |
|---|---|---|
| `TS2CPP_NO_EQUIVALENT` | warning | Feature has no C++ equivalent; placeholder emitted |
| `TS2CPP_APPROXIMATE` | warning | Feature is approximated; semantics may differ |
| `TS2CPP_UNSUPPORTED_EXPR` | warning | (existing) Catch-all from inline fallback |
| `TS2CPP_UNSUPPORTED_STMT` | warning | (existing) Catch-all from inline fallback |
| `TS2CPP_UNSUPPORTED_TOPLEVEL` | warning | (existing) Catch-all from inline fallback |

The existing codes remain as fallbacks for edge cases not covered by the registry.

## Design Decisions

- **Pre-scan is additive**: It does NOT replace the existing inline detection. Both systems coexist. The pre-scan provides comprehensive, centralized reporting; the inline handlers provide the actual IR lowering (placeholder emission).
- **Accept duplicate warnings initially**: The pre-scan uses distinct diagnostic codes (`TS2CPP_NO_EQUIVALENT`, `TS2CPP_APPROXIMATE`) while inline fallbacks use `TS2CPP_UNSUPPORTED_EXPR`. Both may fire for the same node. This is acceptable — the pre-scan message is clearer and appears first. Position-based deduplication can be a follow-up improvement.
- **Testing**: Unit tests in the existing `tests/` directory following project conventions. Test the pre-scan function directly with source strings containing known unsupported features and verify the correct diagnostics are produced.
