# Plan: Cuttlefish Transpiler Feature Gap Implementation

## Scope

All partially-supported and unsupported features that belong in the transpiler package (`packages/cuttlefish`), excluding platform-specific items (async/await, dynamic import, for-await-of, import.meta/new.target, globalThis, JSX, with statement, ambient modules).

Target: GCC 15 with C++23 support.

---

## Phase 1: High-Value, Low-to-Medium Effort

### 1A. Computed Enum Values

**Problem:** Only `NumericLiteral` and `-NumericLiteral` are evaluated in enum initializers. Expressions like `1 << 3`, `A | B`, references to prior enum members, and arithmetic are silently dropped (member gets `value: undefined`).

**Files to modify:**
- `packages/cuttlefish/src/ir/declaration-builders.ts` — `enumDeclarationToIR` (lines 397-445)

**Implementation:**
1. Add a `evaluateConstExpr(expr: ts.Expression, memberMap: Map<string, number>): number | undefined` helper function in `declaration-builders.ts`
2. Support these expression kinds:
   - `NumericLiteral` → parse number (existing)
   - `PrefixUnaryExpression` with `-` → negate (existing, extend to `+`, `~`)
   - `BinaryExpression` → evaluate both sides, then apply operator (`+`, `-`, `*`, `/`, `%`, `|`, `&`, `^`, `<<`, `>>`, `||`, `&&`)
   - `Identifier` → look up in `memberMap` (reference to prior enum member)
   - `PropertyAccessExpression` → resolve `EnumName.Member` from previously declared enums
   - `ParenthesizedExpression` → unwrap and recurse
3. Replace the current two-case `if/else if` in the enum member loop with a call to `evaluateConstExpr`
4. If `evaluateConstExpr` returns `undefined`, emit a diagnostic warning and fall back to auto-increment

**Test:** Add test `30-computed-enums.test.ts` to `packages/framework-native/tests/` with:
- `1 << 3`, `A | B`, `A + B` computed values
- Reference to prior enum member: `C = A | B`
- Parenthesized: `D = (1 << 4) | 0x0F`

### 1B. Rest Parameter Emission as C++ Variadic / `std::initializer_list`

**Problem:** `isRest` is tracked in `ParameterIR` but never used during rendering. A rest parameter `...args: number[]` is emitted as a plain parameter `std::vector<number> args` instead of a C++ variadic pack.

**Decision:** Since TS rest params are always typed as arrays, the most idiomatic C++ mapping is `std::vector<T>` parameter — which is what already happens. The real gap is **spread-into-call** (e.g., `fn(...args)`) which already works for `std::vector` via `.begin()/.end()`. 

**What to fix:**
1. `packages/cuttlefish/src/emit/statement-renderer.ts` — In `renderParameters` (wherever parameter lists are rendered), when `isRest` is true, emit `const std::vector<CppType>& name` instead of just `CppType name` to make the array parameter explicit
2. `packages/cuttlefish/src/emit/emitters/class-emitter.ts` — Same for constructor/method parameters with `isRest`
3. This is mostly a cosmetic/type-correctness fix since the current output already works

**Test:** Add a test case in `13-functions-collections.test.ts` or a new `31-rest-spread.test.ts`:
- Function with rest param called with array spread
- Verify the vector parameter type is correct in emitted C++

### 1C. Nested Namespaces

**Problem:** Nested `namespace A { namespace B { } }` or dotted `namespace A.B { }` is silently skipped.

**Files to modify:**
- `packages/cuttlefish/src/ir/namespace-builder.ts` — line 41-44 (`continue` for `ModuleDeclaration`)

**Implementation:**
1. Instead of `continue`, recursively call `namespaceToIR` for nested `ModuleDeclaration` nodes
2. The parent namespace IR's `children` array (new field) holds nested namespace IRs
3. For dotted namespace names (`namespace A.B.C {}`), TypeScript flattens these into nested `ModuleDeclaration` nodes automatically, so recursive handling covers both syntax forms
4. Add `children?: NamespaceIR[]` to the `NamespaceIR` type in the API

**Files to modify:**

### 1D. Labeled Break/Continue → C++ `goto`

**Problem:** Labeled `break`/`continue` emit as a comment. C++ supports `goto` which can implement this.

**Approach:** When a labeled `break` is encountered:
- `break outerLoop;` → `goto __break_outerLoop;`
- `continue outerLoop;` → `goto __continue_outerLoop;`
- The `LabeledIR` node's body (the loop) gets suffix labels:
  - `__continue_outerLoop:` at the loop's continue point (top of for/while, bottom of do-while)
  - `__break_outerLoop:` after the loop body

**Files to modify:**
- `packages/cuttlefish/src/emit/statement-renderer.ts` — lines 260-266: emit `goto __break_LABEL` / `goto __continue_LABEL` instead of comment
- `packages/cuttlefish/src/emit/emitters/line-appender.ts` — after emitting loop body under a label, emit `__break_LABEL:` and `__continue_LABEL:` at appropriate positions
- `packages/cuttlefish/src/ir/transformers/control-flow.ts` — labeled statement handler: propagate the label down to the inner loop IR nodes so the emitter knows which loops have labeled exits

**Test:** Add test case in `06-loops.test.ts`:
```ts
outerLoop: for (let i = 0; i < 3; i++) {
  for (let j = 0; j < 3; j++) {
    if (i === 1 && j === 1) break outerLoop;
  }
}
```

### 1E. Class Expressions → Named Class Declaration

**Problem:** `const C = class { ... }` is unsupported.

**Files to modify:**
- `packages/cuttlefish/src/ir/expression-to-ir.ts` — lines 1060-1062 (class expression handler)

**Implementation:**
1. Generate a synthetic class name: `__anonClass_N` (where N is a counter)
2. Call `classDeclarationToIR` with the class expression node (treating it like a declaration)
3. Push the class IR to the hoisted declarations list (via `addHoistedClass` or similar)
4. Return `{ kind: "identifier", value: "__anonClass_N" }` as the expression result (the variable holds the class name, which in C++ is the type itself)

**Test:** Add to `07-classes.test.ts`:
```ts

  value: number;
  constructor(v: number) { this.value = v; }
};
const obj = new MyType(42);
return obj.value;  // → 42
```

### 1F. `delete` on Plain Objects (Struct Fields)

**Problem:** `delete obj.prop` on non-map types emits unsupported warning. In C++, you can't delete struct fields.

**Decision:** The correct behavior is:
1. If the object is a `std::map` → `obj.erase(key)` (already works)
2. If the object is a struct → reset the field to its default value (0, "", false, nullptr) and emit a warning
3. If the type is unknown → emit `/* delete not supported */` with a diagnostic

**Files to modify:**
- `packages/cuttlefish/src/ir/expression-to-ir.ts` — `DeleteExpression` handler (lines 1065-1097)

**Implementation:**
1. When `delete` targets a property on a non-map/set/vector type:
   - If the field type is known (from `activeLocalTypes`/`activeGlobalTypes`), emit a `raw` expression that assigns the default value: `(obj.prop = 0, true)`
   - If unknown, emit `/* delete unsupported */` with diagnostic
2. Map common types to defaults: numeric → `0`, string → `""`, boolean → `false`, pointer → `nullptr`

**Test:** Minimal — `delete` on structs is inherently limited. Document as a known semantic difference.

## Phase 2: High-Value, Medium Effort

### 2A. Optional Chaining — Proper Short-Circuit Chains

**Problem:** `a?.b?.c?.d` produces a single `(cuttlefish_exists(a) ? a->b->c->d : 0)` which crashes if `a->b` is null.

**Approach:** Walk the optional chain and emit nested ternaries:
```cpp
auto __oc_tmp = a;
(cuttlefish_exists(__oc_tmp) ? (
  auto __oc_tmp2 = __oc_tmp->b;
  (cuttlefish_exists(__oc_tmp2) ? __oc_tmp2->c->d : nullptr)
) : nullptr)
```

This is tricky in C++ because ternaries can't contain statements. The practical approach:

**Implementation:**
1. In `expression-to-ir.ts`, detect full optional chains by walking up from `?.` nodes
2. For each chain link, generate a prelude statement that evaluates the receiver into a temp variable: `auto __oc_N = expr;`
3. The final expression is a chain of ternaries: `cuttlefish_exists(__oc_1) ? (cuttlefish_exists(__oc_2) ? __oc_2->prop : nullptr) : nullptr`
4. Use the existing `pushPrelude` mechanism in `ExpressionRenderer` to emit the temp variable declarations before the containing statement

**Files to modify:**
- `packages/cuttlefish/src/ir/expression-to-ir.ts` — optional chain handling (lines ~440-456 and 836-844)
- `packages/cuttlefish/src/emit/expression-renderer.ts` — handle new `optional_chain` IR kind

**New IR node** (in `ir-core.ts`):
```ts
| { kind: "optional_chain"; links: { receiver: ExpressionIR; access: string; isCall?: boolean; callArgs?: ExpressionIR[] }[]; fallback: ExpressionIR }
```

**Test:** Extend `12-modules-types.test.ts` or add to `10-expressions.test.ts`:

### 2B. Generic Type Parameters → C++ Templates

**Problem:** `function identity<T>(x: T): T` loses type info; `type Pair<T, U> = { first: T; second: U }` is skipped entirely.

**Implementation:**

1. **Function templates:**
   - `function-builder.ts` already captures `typeParameters` on `FunctionIR`
   - Modify function emission in `line-appender.ts` / `statement-renderer.ts` to emit `template<typename T>` before the function when `typeParameters` is present
   - Type resolution: when a type reference matches a type parameter name, emit it as-is (the template parameter name)

2. **Class templates:**
   - `declaration-builders.ts` — `classDeclarationToIR` should capture `typeParameters` from `node.typeParameters`
   - Add `typeParameters?: string[]` to `ClassIR`
   - `class-emitter.ts` — emit `template<typename T>` before `class ClassName`
   - Field types that reference template params are emitted as-is

3. **Type alias templates:**
   - `declaration-builders.ts` — `typeAliasDeclarationToIR` currently **skips** parameterized aliases (line 523-525). Remove the skip.
   - Add `typeParameters?: string[]` to `TypeAliasIR`
   - Emit `template<typename T>` using a `struct` with template parameters

4. **Type resolution changes** (`type-resolution.ts`):
   - Add a `typeParametersInScope: Set<string>` parameter to `typeNodeToCppType`
   - When a `TypeReferenceNode`'s name matches a type parameter in scope, return it as-is (passthrough)
   - Thread `typeParametersInScope` through all call sites in declaration-builders, function-builder, namespace-builder, etc.

**Files to modify:**
- `packages/cuttlefish/src/api/shared/ir-core.ts` or API types — add `typeParameters?: string[]` to `ClassIR`, `FunctionIR`, `TypeAliasIR`
- `packages/cuttlefish/src/ir/type-resolution.ts` — add `typeParametersInScope` parameter
- `packages/cuttlefish/src/ir/declaration-builders.ts` — capture class/type alias type params, pass to type resolution
- `packages/cuttlefish/src/ir/function-builder.ts` — pass type params to type resolution
- `packages/cuttlefish/src/ir/namespace-builder.ts` — pass type params to type resolution
- `packages/cuttlefish/src/emit/statement-renderer.ts` — emit `template<typename...>` prefix for function definitions
- `packages/cuttlefish/src/emit/emitters/class-emitter.ts` — emit `template<typename...>` prefix for class definitions

### 2C. `super.method()` Full Support

**Problem:** `super` resolves to the parent class name as a raw string. This works for `super.method()` → `BaseClass::method()` but fails for `super()` outside constructors and produces confusing code for `super.property`.

**Current state:** `super` in constructors works (emits `: Base(args)` initializer). `super.method()` works via raw text resolution. The gap is primarily around `super` in nested arrow functions within methods.

**Implementation:**
1. Verify that `super.method()` calls correctly emit `BaseClass::method(this->...)` for methods that need `this`
2. For `super.property` access → emit `BaseClass::property` (already works via raw text)
3. For `super` used in arrow functions inside methods → need to capture the extends class name at the class level and use it in nested contexts

**Files to modify:**
- `packages/cuttlefish/src/ir/expression-to-ir.ts` — verify and enhance `SuperKeyword` handling (lines 1122-1128)

## Phase 3: Medium-Value, Medium-to-High Effort

### 3A. Generators / `yield` → C++23 Coroutines

**Problem:** No handling for `function*`, `yield`, or `yield*`.

**C++23 Mapping:** GCC 15 supports `<coroutine>`. Map:
- `function*` → coroutine that returns a generator type
- `yield expr` → `co_yield expr`
- `yield* iter` → iterate and `co_yield` each element
- `.next()` → resume coroutine, return `{ value, done }`

**Implementation:**

1. **New IR nodes** (`ir-core.ts`):
   ```ts
   | { kind: "yield"; value: ExpressionIR; isDelegate?: boolean }
   ```
   Add to `StatementIR`:
   ```ts
   | { kind: "yield"; value?: ExpressionIR; isDelegate?: boolean; sourceSpan: SourceSpan; ... }
   ```

2. **Function detection** (`function-builder.ts`, `declaration-builders.ts`):
   - Detect `asteriskToken` on `FunctionDeclaration` / `MethodDeclaration`
   - Add `isGenerator: boolean` to `FunctionIR` and method IR

3. **Expression-to-IR** (`expression-to-ir.ts`):
   - Handle `YieldExpression` → `{ kind: "yield", value: ... }`
   - Handle `SpreadElement` in `yield*` context

4. **Preamble** (`cpp-emitter.ts`):
   - Emit a `__tc_Generator<T>` coroutine wrapper class with `promise_type`, `co_yield` support, and `.next()` method
   - Only emit if any generator functions are detected

5. **Statement rendering** (`statement-renderer.ts`):
   - `yield expr` → `co_yield expr;`
   - `yield* iter` → `for (auto& __elem : iter) co_yield __elem;`

6. **Function rendering**:
   - Generator functions emit return type `__tc_Generator<T>` instead of `void`/`T`
   - Function body becomes a coroutine body

**Files to modify:**
- `packages/cuttlefish/src/api/shared/ir-core.ts` — new `yield` statement IR
- `packages/cuttlefish/src/ir/expression-to-ir.ts` — `YieldExpression` handler
- `packages/cuttlefish/src/ir/function-builder.ts` — `isGenerator` detection
- `packages/cuttlefish/src/ir/declaration-builders.ts` — method `isGenerator`
- `packages/cuttlefish/src/emit/statement-renderer.ts` — `yield` rendering
- `packages/cuttlefish/src/emit/cpp-emitter.ts` — generator preamble
- `packages/cuttlefish/src/emit/emitters/line-appender.ts` — yield statement handling

**Test:** Add test `33-generators.test.ts`:
```ts

  for (let i = 1; i <= n; i++) yield i;
}

// C++ test would verify gen.next().value === 1, etc.
```

Note: Since the test framework compiles and runs C++ via `exec`, generator tests need to produce a simple verifiable result (e.g., sum all yielded values).

### 3B. `Object.keys/values/entries` on Plain Objects (Structs)

**Problem:** Only works on `std::map`. For `const obj = { a: 1, b: 2 }; Object.keys(obj)` emits unsupported.

**Implementation:**
1. Track struct-like object literal types and their field names
2. When `Object.keys(obj)` is called on a known struct type, emit `std::vector<std::string>{ "a", "b" }`
3. When `Object.values(obj)` is called, emit `std::vector<T>{ obj.a, obj.b }` (type must be uniform or use `std::variant`)
4. When `Object.entries(obj)` is called, emit vector of pairs

**Approach:**
- The type system already tracks object types via `activeLocalTypes`/`activeGlobalTypes`
- Need to also track **field lists** for struct types
- Add a `structFields: Map<string, string[]>` to the compilation context
- When an object literal is assigned to a typed variable, record its field names

**Files to modify:**
- `packages/cuttlefish/src/ir/build-ir-state.ts` — add `structFields` to context
- `packages/cuttlefish/src/ir/expression-to-ir.ts` — Object.keys/values/entries handler, look up struct fields
- `packages/cuttlefish/src/ir/transformers/variables.ts` — record struct field names when processing object literal initializers

**Test:** Add to `11-arrays.test.ts` or new test:
```ts
const obj = { x: 1, y: 2, z: 3 };

Object.values(obj);        // iterate values
```

### 3C. Declaration Merging

**Problem:** TS allows merging interfaces, namespaces with classes, etc. The transpiler processes each declaration independently.

**Implementation:**
1. **Interface merging:** When multiple `interface Foo {}` declarations exist, merge their members
2. **Namespace-class merging:** `namespace Foo {}` + `class Foo {}` → class with static namespace members
3. **Namespace-namespace merging:** Multiple `namespace Foo {}` → single namespace with all members

**Approach:**
- In `build-ir.ts`, after collecting all top-level declarations, run a merge pass:
  - Group declarations by name
  - Merge interfaces: combine fields and methods
  - Merge namespaces: combine all children
  - Namespace + class: add namespace exports as static class members

**Files to modify:**
- `packages/cuttlefish/src/ir/build-ir.ts` — add merge pass after main collection
- `packages/cuttlefish/src/ir/declaration-builders.ts` — add `mergeInterfaceIR`, `mergeNamespaceIR` helpers

**Test:** Add test case:
```ts
interface Point { x: number; }
interface Point { y: number; }
const p: Point = { x: 1, y: 2 };
```

### 3D. Decorators (beyond `@register`)

**Problem:** Only `@register` is handled. Standard decorators (TC39 / TS experimental) are ignored.

**Decision:** Support a minimal set of built-in decorators that map to C++ concepts:
- `@inline` → `__attribute__((always_inline))` or `[[gnu::always_inline]]`
- `@nodiscard` → `[[nodiscard]]`
- `@deprecated` → `[[deprecated]]`
- `@sealed` → `final` class
- Custom decorators → emit as C++ attributes or preprocessor macros (user-extensible)

**Implementation:**
1. In `declaration-builders.ts`, extract all decorators from class/method/property nodes
2. Add `decorators?: string[]` to `ClassIR`, method IR, field IR
3. In emitters, map decorator names to C++ attributes

**Files to modify:**
- `packages/cuttlefish/src/ir/declaration-builders.ts` — decorator extraction
- `packages/cuttlefish/src/api/shared/ir-core.ts` or API types — `decorators` field
- `packages/cuttlefish/src/emit/emitters/class-emitter.ts` — emit C++ attributes
- `packages/cuttlefish/src/emit/statement-renderer.ts` — emit attributes on functions

**Test:** Add test `34-decorators.test.ts`

## Phase 4: Type-Level Improvements (Low Priority)

These are compile-time-only TypeScript features that currently fall back to `auto`. Improving them makes generated C++ more type-precise but doesn't change runtime behavior.

### 4A. Indexed Access Types (`T[K]`)

**Files:** `packages/cuttlefish/src/ir/type-resolution.ts`

When a `IndexedAccessTypeNode` is encountered:
1. Resolve the object type (look up in `typeAliasNodes` or `activeLocalTypes`)
2. Resolve the index type
3. If both are concrete, look up the property type and return it
4. Otherwise fall back to `auto`

### 4B. `keyof T` Operator

**Files:** `packages/cuttlefish/src/ir/type-resolution.ts`

When `TypeOperatorNode` with `keyof` is encountered:
1. Resolve the inner type
2. If it's a known struct/object type with fields, emit a string union or `auto`
3. This is primarily useful for generic constraints — `auto` fallback is acceptable

### 4C. Conditional Types (`T extends U ? X : Y`)

**Files:** `packages/cuttlefish/src/ir/type-resolution.ts`

When `ConditionalTypeNode` is encountered:
1. Check if the `checkType` is a type parameter in scope
2. If both branches resolve to concrete types, emit the true branch (optimistic)
3. Otherwise `auto`

### 4D. Template Literal Types

**Files:** `packages/cuttlefish/src/ir/type-resolution.ts`

When `TemplateLiteralTypeNode` is encountered → `auto` (no C++ equivalent). This is purely a TS type-system feature.

### 4E. `infer` Keyword

**Files:** `packages/cuttlefish/src/ir/type-resolution.ts`

No C++ equivalent. `auto` fallback is correct.

### 4F. `as const`

**Files:** `packages/cuttlefish/src/ir/expression-to-ir.ts`

When `AsExpression` with `const` type assertion is encountered:
1. Unwrap as before (already works)
2. Optionally: narrow literal types (string → `const char*`, number → literal value)
3. Low priority since unwrapping already produces correct runtime code

## Key Architecture Decisions

1. **C++23 assumptions:** Use `<coroutine>` for generators, `[[nodiscard]]`/`[[deprecated]]` attributes, `std::variant` for unions
2. **Type parameter scoping:** Thread `typeParametersInScope: Set<string>` through `typeNodeToCppType` to preserve template parameter names
3. **Optional chaining:** Use temp variables via prelude mechanism rather than complex nested ternary expressions
4. **Generators:** Implement a minimal `__tc_Generator<T>` coroutine wrapper rather than trying to match the full JS generator protocol
5. **Declaration merging:** Post-processing merge pass in `build-ir.ts` rather than inline during parsing
6. **Backward compatibility:** All changes must not break existing test suite (29 tests). New tests are additive.
