# Plan: Fix Identified TypeScript Feature Gaps in Cuttlefish

## Summary
Fix 12 missing TypeScript features in the cuttlefish transpiler, prioritized by correctness impact and ease of implementation.

---

## 1. CRITICAL: Labeled break/continue (silent miscompilation)

**Problem:** `break outerLoop;` and `continue outerLoop;` silently drop the label, emitting bare `break;`/`continue;` that targets the wrong loop.

**Files to change:**
- `packages/cuttlefish/src/api/shared/ir-core.ts` — Add `label?: string` to `BreakIR` and `ContinueIR` interfaces (lines 199-211)
- `packages/cuttlefish/src/ir/transformers/control-flow.ts` — Extract `statement.label?.text` from break/continue statements (lines 347-364)
- `packages/cuttlefish/src/emit/statement-renderer.ts` — Emit `break <label>;` and `continue <label>;` when label present (lines 260-266)

**Changes:**
```
// ir-core.ts
export interface BreakIR {
  kind: "break";
  sourceSpan: SourceSpan;
  leadingComments?: string[];
  trailingComments?: string[];
  label?: string;  // ADD
}

export interface ContinueIR {
  kind: "continue";
  sourceSpan: SourceSpan;
  leadingComments?: string[];
  trailingComments?: string[];
  label?: string;  // ADD
}
```
```
// control-flow.ts — in isBreakStatement handler:
return [{
  kind: "break",
  sourceSpan: makeSourceSpan(statement, fileName, sourceText),
  leadingComments: comments.leadingComments,
  trailingComments: comments.trailingComments,
  label: statement.label?.text,  // ADD
}];

// same for isContinueStatement handler
```
```
// statement-renderer.ts — in break/continue handlers:
if (statement.kind === "break") {
  return statement.label ? `break ${statement.label};` : "break;";
}
if (statement.kind === "continue") {
  return statement.label ? `continue ${statement.label};` : "continue;";
}
```

Note: C++ requires labels on loops, not on break/continue. But `break label;` is NOT valid C++ — C++ only has plain `break`/`continue`. So we need a different approach: convert labeled break/continue into a flag-based mechanism using bool guards, OR just emit a diagnostic warning that labeled breaks are not supported. The simplest correct approach is to emit a warning diagnostic and drop the label (current behavior) but make it explicit rather than silent.

**Revised approach:** Since C++ has no labeled break/continue, the correct fix is:
1. Still add `label?: string` to the IR types for traceability
2. In `control-flow.ts`, extract and store the label
3. In `statement-renderer.ts`, when label is present, emit a warning and fall back to plain `break;`/`continue;`
4. This makes the miscompilation explicit rather than silent

## 3. `super` keyword in method bodies

**Problem:** `super.method()` in derived class method bodies renders as literal `super` in C++ (invalid). Need to rewrite to `ParentClass::method()`.

**Files to change:**
- `packages/cuttlefish/src/ir/expression-to-ir.ts` — Add `SuperKeyword` handler that returns `{ kind: "raw", value: parentClassName }`
- Need access to current class's `extendsClass` from the build-ir-state module

**Approach:** Add an `activeExtendsClass` variable to `build-ir-state.ts` (similar to `activeEnumNames`). Set it in `classDeclarationToIR` when processing class methods. In expression-to-ir, check for `SuperKeyword` and emit the parent class name.

**Changes:**
1. `build-ir-state.ts` — Add `export let activeExtendsClass: string | undefined = undefined;`
2. `declaration-builders.ts` — Set/clear `activeExtendsClass` around method processing in `classDeclarationToIR`
3. `expression-to-ir.ts` — Add handler:
```ts
if (expr.kind === ts.SyntaxKind.SuperKeyword) {
  if (activeExtendsClass) {
    return { kind: "raw", value: activeExtendsClass };
  }
  return emitUnsupportedExpression("super keyword outside of class method");
}
```

## 9. Global utility functions (parseInt, parseFloat, etc.)

**File:** `packages/cuttlefish/src/ir/expression-to-ir.ts`
**Location:** In the `isCallExpression` block, after the `Error` handler (around line 481)

**Change:**
```ts
if (ts.isIdentifier(expr.expression)) {
  const fnName = expr.expression.text;
  if (fnName === "parseInt" && expr.arguments.length >= 1) {
    const argText = renderExprAsText(expressionToIR(expr.arguments[0], sourceText, diagnostics, pointerVars));
    return { kind: "raw", value: `atoi(${argText})` };
  }
  if (fnName === "parseFloat" && expr.arguments.length >= 1) {
    const argText = renderExprAsText(expressionToIR(expr.arguments[0], sourceText, diagnostics, pointerVars));
    return { kind: "raw", value: `atof(${argText})` };
  }
  if (fnName === "isNaN" && expr.arguments.length >= 1) {
    const argText = renderExprAsText(expressionToIR(expr.arguments[0], sourceText, diagnostics, pointerVars));
    return { kind: "raw", value: `std::isnan(${argText})` };
  }
  if (fnName === "isFinite" && expr.arguments.length >= 1) {
    const argText = renderExprAsText(expressionToIR(expr.arguments[0], sourceText, diagnostics, pointerVars));
    return { kind: "raw", value: `std::isfinite(${argText})` };
  }
  if (fnName === "Number" && expr.arguments.length >= 1) {
    return expressionToIR(expr.arguments[0], sourceText, diagnostics, pointerVars);
  }
  if (fnName === "String" && expr.arguments.length >= 1) {
    const argIR = expressionToIR(expr.arguments[0], sourceText, diagnostics, pointerVars);
    return { kind: "template_string", expression: argIR };
  }
  if (fnName === "Boolean" && expr.arguments.length >= 1) {
    const argIR = expressionToIR(expr.arguments[0], sourceText, diagnostics, pointerVars);
    return { kind: "raw", value: `static_cast<bool>(${renderExprAsText(argIR)})` };
  }
}
```

Also need `<cmath>` for `std::isnan`/`std::isfinite` — these already trigger `hasStdMathCalls` via the `std::` prefix in the MATH_PATTERN.
