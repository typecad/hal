## F5 debugging is now west-owned and board-agnostic (cortex-debug external-server mode)

The board-specific debug knowledge moved from cuttlefish into Zephyr where it lives: `west debugserver` now serves the gdb connection using the board's own runner configuration, and the generated launch.json connects cortex-debug to it (`servertype: 'external'` + `gdbTarget: localhost:3333`). What was deleted is as important as what was added — the hand-rolled machinery that reconstructed what west already knows is gone: the openocd cfg generation (probe-table cfg assembly, gdb-attach event stripping, adapter-speed constants, the RTOS line), the per-architecture gdb SDK-layout discovery, and the board-name allowlist in `debugMode()` (the `esp32s3*`/`blackpill*` special cases the repo's own all-boards-equal rule flagged).

gdb mode is now a fact, not a name: any board whose probe-method table carries a debug-capable entry (1,022 of the catalog's boards) gets native GDB debugging — the gdb binary comes from the build's own `runners.yaml` (west's resolution, correct per-architecture by construction), and the Zephyr RTOS awareness and adapter quirks come from west's runner. `debugMode()` reads the board's facts; xiao_ble and the plain esp32_devkitc, previously name-gated to printf, now debug.

New `cuttlefish debug-server start|stop` wraps `west debugserver`: a ready marker gates the VS Code background task (the debug session waits for it before connecting; readiness is polled on west's openocd tcl port — the gdb server takes one client, so probing it directly logged `attempted 'gdb' connection rejected` and could race the real gdb connection for the slot), the SRST quirk is applied server-side from the board's own method data (an unwired-NRST `reset_config srst_only` cfg makes `reset init` time out — the same condition the flash path has always handled), gdb-attach/detach events are neutralized for the IDE (west's `--cmd-pre-init` lands after the board cfg, so the overrides win), and orphaned servers are reclaimed by port ownership when a killed task terminal leaves openocd behind a stale pidfile. The launch entry gains a `postDebugTask` that stops the server when the session ends. Create-time starter entries carry a best-effort `gdbPath` resolved from the installed SDK and the board's silicon (VS Code snapshots launch.json before running the preLaunchTask, and the task is what produces the build — without a starter path the very first F5 on a fresh project would fail to find gdb); the first build's west-resolved gdb replaces any wrong guess, and a gdb mismatch triggers the plain-build artifact rewrite alongside the existing upgrade-on-first-build path.

The F5 wiring is a single task chain: the launch entry's `preLaunchTask` IS the background server task, whose `dependsOn` runs build + flash first — VS Code proceeds to connect gdb exactly when the ready marker appears, and `postDebugTask` stops the server. The task runs with `NO_COLOR=1` — chalk's ANSI codes break the background problem-matcher patterns (the transpile banner's escape byte defeats the `^` anchor, VS Code never sees begins→ends, and F5 falls back to the "task has not exited — debug anyway?" prompt). Flashing reclaims the gdb port up front (a live or orphaned debug server holds the probe exclusively and openocd fails with `LIBUSB_ERROR_ACCESS` before anything else can help — a VS Code window reload kills task terminals without killing their children on Windows, leaving exactly such orphans).

Validated on hardware end to end (blackpill_f401cc over ST-Link): build → flash → `debug-server start` → gdb attach with exactly the generated post-attach commands → hardware breakpoint at `main` resolving to the TypeScript source line → clean detach → `debug-server stop` with the full process tree reaped.
